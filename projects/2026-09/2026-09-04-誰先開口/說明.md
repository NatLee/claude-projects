# 誰先開口 🍜（2026-09-04・生活痛點小工具）

## 故事線

- **鉤子**：第一屏不解釋任何名詞，只給一個所有人都經歷過的場景——「那趟旅行是三個星期前的事了。錢還沒清。不是因為有人想賴帳，是因為到現在沒有人算得出來誰該給誰多少。」
- **鋪陳**：把讀者放進那個群組。敘事容器是一串**假的聊天訊息**：七則「我先付了」的訊息一則則浮出來，每一則後面掛一張帳的標籤（誰付、多少、分給誰）。最後兩則是「所以…到底誰欠誰？」「我明天算一下」——然後時間戳跳過三個星期，只剩一行「已讀 6」。沒有人再說話。
- **轉折起點**：按下按鈕，七則訊息被畫成線。六個人繞成一圈，**27 條**細細的欠款弧線一條一條長出來，越畫越亂，數字滾到 27。「難怪三個星期沒有人想先開口。」
- **轉折**：揭曉那個大部分人不知道的事實——**你根本不需要知道誰欠誰**，你只需要知道每個人多付了多少、少付了多少。使用者親手按下「把線折起來」：27 條線同時往回縮、消失，計數滾回 0，底下浮出六條淨額長條（正的綠、負的紅），加起來剛好是 0。
- **高潮**：「結清」。規則失禮地簡單——欠最多的付給該收最多的，付到一邊歸零，然後重來。四步動畫，長條一根根縮回零、名字一個個變灰，轉帳清單一列列滑進來。大字落地：**27 → 4**。
- **回味一（把懸念收掉）**：「等等，這真的是最少的嗎？」按下去，頁面當場把六個人拆成 203 種分組、跑 364 次比對，回答：4 筆就是最少，沒有更漂亮的解。
- **回味二（真的能用）**：最後給一個可複製的訊息框，話已經寫好了。再往下是同一套演算法做成的工具——填自己的人和帳，算出最少轉帳，一樣附一段寫好的話，存在瀏覽器裡。
- **記憶點（回馬槍）**：剛剛那個「把所有分組都試一遍」的動作有名字，叫 NP-complete；六個人 203 種，十二個人四百多萬種，二十個人五十兆種。連 Splitwise 都沒有真正解開它。**但那筆錢卡了三個星期，其實從來不是因為數學——六個人裡沒有人不會算除法，他們卡住的地方是誰要當第一個開口的人。現在那段話已經寫好了，你只要按複製。**

## 這是什麼

一頁「分帳債務簡化」的互動敘事＋可用小工具。敘事容器是**一串假的群組聊天記錄**，高潮是使用者親手把 27 條交錯的欠款折疊成 4 次轉帳，並用暴力搜尋當場證明 4 就是最少。最後把同一套演算法開放給讀者用在自己的聚餐上，並直接生成一段可以貼回群組的訊息。

## 怎麼玩

1. 讀完群組裡的七則訊息（每則下面是那筆帳的細節）。
2. 按「把七則訊息畫成線」，看 27 條欠款弧線長出來。
3. 按「把線折起來」，線消失，六個淨額浮現，總和為 0。
4. 按「結清」，四步結清動畫跑完，看到 **27 → 4**。
5. 按「等等，這真的是最少的嗎？」讓頁面當場暴力驗證。
6. 按「複製這段話」拿走寫好的訊息。
7. 往下捲到「換你的那一頓」：加人、加帳（可指定誰付、分給誰），即時算出最少轉帳與可複製訊息。

## 為什麼有趣

分帳是個假裝成數學題的社交題。真正讓錢卡住的不是計算難度——是「開口」的心理成本。這一頁刻意把兩件事都做完：先用視覺把「27 條線」壓成「4 筆轉帳」（讓那個混亂**看起來**消失），再把最後一哩路（那句話）直接寫好交到讀者手上。

而底下的數學也剛好夠漂亮：淨額結算把 O(人數²) 條債務壓成 n 個數字，是這題唯一真正的洞見；而「筆數能不能再更少」則突然掉進 NP-complete，可以用來說明「直覺上很簡單的日常問題，理論上可以很硬」。

## 演算法與方法論

金額一律以「分」為整數單位運算，避免浮點誤差。

1. **`splitShares(total, n)`**：整數平均分攤，餘數逐一分給前面的人。守恆保證：分出去的總和恆等於原金額（隨機 3000 組驗證通過）。
2. **`computeNets(nPeople, bills)`**：每個人的淨額 = 他付出去的 − 他應該分攤的。**所有人的淨額加起來恆為 0**，這是整頁的支點。
3. **`greedySettle(net)`**：貪婪法。每一輪讓「欠最多的人」付給「該收最多的人」，付到其中一邊歸零。最多 n−1 筆（n 為淨額非零的人數）。Splitwise 用的也是這一類方法。
4. **`minSettle(net)`**：真正的最小值。**最少轉帳筆數 = 非零人數 − 最大「零和分組」數**——因為每一個能自己抵銷乾淨的小圈子，內部只需要 (組員數 − 1) 筆。用 bitmask DP 在 O(3ⁿ) 內求最大零和分組數；本頁對 14 人以內求精確解（14 人實測約 2 ms），超過就退回貪婪近似並在介面上老實說明。
5. **`bell(n)`**：貝爾數，即「把 n 個人分成任意組別」的方法數，用來誠實地講出「試過幾種分組」——B(6)=203、B(12)=4,213,597、B(20)=51,724,158,235,372。

**複雜度**：找出最少轉帳筆數等價於「最大零和集合分裝（zero-sum set packing）」，是 NP-complete；它至少和子集合加總（subset sum / partition）一樣難。

**驗證**：核心四個函式抽成純函式，用 node 跑過斷言——
- 隨機 3000 組零和淨額（2～10 人）：貪婪與最佳解都能把每個人結算到 0、金額皆為正、且貪婪的筆數從不小於最佳解；其中約 14% 的情況貪婪確實不是最佳（所以「證明最少」那顆按鈕不是裝飾）。
- 故事那組資料：淨額 阿哲 +4,995／小K −1,965／Mei −1,245／老吳 −645／Ryan −1,785／Nana +645，總和 0；27 條欠款；貪婪 4 筆＝最佳 4 筆（因為只有兩個債權人，最大零和分組數就是 2，6 − 2 = 4）。
- 另外用 jsdom 實際載入整頁跑一次流程（reduced-motion 與完整動畫兩種模式各一次），確認畫線、折疊、結清、證明、工具的加人／刪人／擋下 0 元／擋下未選分攤對象都正確，且 console 無錯誤。這一輪抓到一個真實的 bug：同一格數字上有兩個滾動動畫在跑時，舊的會在結束時把新值蓋回去——已改成每個節點只允許一個滾動動畫，並移除折疊時多餘的延遲。

## 資料來源

- Splitwise 的債務簡化（debt simplification）採貪婪／最小成本流一類的近似解法，並非精確最小化。
- Yao, W. *Settling Debts Efficiently: Zero-Sum Set Packing*（Harvard senior thesis, 2017）：最少轉帳筆數問題等價於零和集合分裝，為 NP-complete。
- LeetCode 465「Optimal Account Balancing」是同一個問題的教科書版本，標準解法即本頁使用的 bitmask DP。
